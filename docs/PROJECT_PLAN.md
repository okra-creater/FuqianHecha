# 项目方案：当前规则版与后续方向

当前交付的是透明规则版：用户提交文字，系统匹配规则、关联已审核资料并一次性生成报告。交互式追问、动态检索和大模型增强属于后续计划。

## 定位与用户

付前核查：帮助准备付款的大学生理解交易中的风险信号，优先覆盖香港线上兼职预付费和租房付款。场景选择是假设，尚无用户访谈或市场验证。

## 问题与使用流程

当前流程：用户粘贴聊天文字 → 系统识别场景并匹配透明规则 → 关联已审核资料 → 生成核查报告和建议追问。当前页面不能接收追问答案并重新分析。

后续设想：加入用户回答或选择不知道的步骤，再根据补充信息生成报告。

报告包含：核查状态、聊天原文证据、资料来源、待确认信息、可操作的核查清单。
未知事实不得默认为不存在；用户说“已核实”仍须标记为用户陈述，不能变成系统外部核验。

## 第一版能力

- 文字输入；网页地区固定为 HK。分析器接收其他地区参数时会说明资料适用限制。
- 识别付款条件、招聘主体/出租方、催促话术和身份核验背景。
- 已审核资料加载与引用。风险信号通过预设映射关联来源；无风险信号时按场景词项检索资料。
- 明显风险出现时先给提示，不强迫用户回答完才提示。
- 无充分证据时给出信息不足报告和建议追问；回答追问的交互流程留待后续。
- 不做账号系统、实时监控、自动转账、银行数据接入。
- 先网页原型，截图识别后置。不得宣称与工行或微信支付有已实现合作。

## 输出契约

status 为 risk_signals（发现风险信号）、insufficient_information（信息不足）、no_obvious_signals（依据已提供信息暂未发现明显信号）之一。
区分状态与不确定性：有明显风险且信息不全时仍可标为 risk_signals，并另列缺失信息。
其余字段：scenario、jurisdiction、signals（description、精确 evidence_quote、source_ids）、unknowns、questions、checklist、limitations。
风险状态不代表刑事定性；no_obvious_signals 不等于安全保证。无概率校准前不输出“诈骗概率 99%”。

## 技术分工与数据

当前使用 Python 透明规则、已审核官方资料摘要和简单网页，不需要大模型 API。后续若接入模型，程序仍须验证结构、原文证据与来源引用。
knowledge/ 是唯一检索数据目录；data/ 是评测案例，禁止混入索引。
开发时默认只用合成或已授权脱敏内容。接入外部模型前说明数据会发送给模型提供方；本地不保存原文并不等于第三方不保留。

## 研究问题与完成标准

当前阶段先验证规则版能否稳定生成可追溯、边界清楚的报告。后续若加入模型，再研究检索与追问能否改善判断和证据质量，并通过基线、检索版、检索加追问版对比验证，不预设一定提升。
第一阶段完成标准：能走通文字核查全流程，引用可定位，原文证据真实存在，缺失信息不臆造。性能结论须待评测，个人贡献须能解释。
